# Selecting products

These rules apply to every store and destination: a price check, a shopping list, or a cart. Apply criteria in this order. A later criterion cannot make up for violating an earlier hard requirement.

1. **Hard prohibitions and exact requirements.** Exclude products that contain an allergen or prohibited ingredient, and products the user explicitly does not want. Preserve exact product and brand requests. If ingredient information is not visible enough to assess the product, skip it and explain why.
2. **Product identity and intended use.** Confirm that the result is the requested food and can be used as requested. A name match is not proof: cheese containing chili is not chili powder; tomato-basil sauce is not dried basil; cat food containing salmon is not salmon fillet.
3. **Required form and attributes.** Match requested fresh/frozen, ready-made/raw, origin, brand, dietary, and other attributes. Treat an attribute as a flexible preference only if the user did not make it mandatory.
4. **Availability at the confirmed store or stores.** Use availability for each confirmed store if the site shows it. Finding an item in a general search does not prove it is available at every store. For comparisons, keep store-specific items, prices, and missing products separate.
5. **Price and budget, when they are part of the user's goal.** Do not assume price is a selection criterion. In a price check, report prices for the suitable product even when the user gave no price criterion; just do not let price pick between options unless asked. If the user asks for the cheapest option or provides a budget/price limit, compare unit prices (€/kg, €/l, or €/item) for suitable alternatives and show package price and size alongside them. Compare unit prices only for equivalent products; account for drained weight where relevant. Check offers, member prices, variable-weight items, and package-label differences. A multi-buy offer (such as 3 for €1) is not the single-item price; do not buy extra packages to reach it unless the user asks, but mention it in the report. If unit price is missing or unreliable, compare package prices only when product type and size are clear; otherwise do not make a price-based choice.
6. **Package size, waste, and shopping total.** Treat the requested quantity as the expected need. Prefer the smallest available package or combination that reasonably meets an approximate quantity and minimizes avoidable surplus; do not upsize solely for a lower unit price. Count the full package price toward the budget and show package size, unit price, and likely leftover when useful. Do not assume surplus will be used later, shared, or gifted. If package choices create a material cost-versus-waste trade-off and the user's priority does not resolve it, choose the package closest to the planned need and report the alternative, with its price and likely leftover, in the final report.
7. **Convenience.** Select ready-to-use or pre-cut food if the user requested it or said they value convenience. Do not assume convenience justifies a higher price. Do not treat frozen and fresh, raw and cooked, or whole and pre-prepared foods as automatically equivalent.

## If no selection criterion was provided

Preserve the exact product the user named. If they gave only a generic item, do not choose an option based on price, origin, brand, preparation level, or another value-based criterion without being asked. If the site requires choosing one option and the user's prior instructions do not resolve it, skip the item and list the suitable options in the final report, so the user can choose without the run stopping halfway. Do not apply a default 20% price threshold or another preference of your own.

## Budget total

When price and quantity are reliably visible, add up the prices of the packages to be added or priced and report the total as an estimate. Say if the amount is partial, uses member prices, or is otherwise uncertain. For variable-weight goods priced per piece, use the site's estimate and say the final amount may vary. Do not include prices the site did not show or assess budget fit based on missing prices. If the budget limit would be exceeded, report the overage and ask the user which savings changes they want. A list, cart, or price-check total is not an order or delivery total: it excludes fees the site has not shown and can change before checkout.

## Comparing stores

- Use the first named store as primary and later stores as comparison candidates unless the user marks another as primary or says the stores are equal alternatives.
- Compare the same requested basket at each named store where possible, using suitable products and the number of full packages needed. Report unavailable items and substitutions separately; do not hide them inside a total.
- Default to one store for the whole basket. Do not choose a larger store just because it may have a wider assortment, and do not split the basket unless the user explicitly asks to consider that option.
- When the user allows split-store shopping, include known extra trip, pickup, or delivery costs. Keep unknown fees and travel costs separate rather than guessing.
- Do not infer the user's location or access to a car. Use a postal code or area they provide for the comparison, and ask before using precise location data.

## Substitutions and uncertainty

Substitute only if the user allows it and the alternative preserves the intended use, dietary requirements, and relevant attributes. For a generic request such as "rice" or "tomato", an ordinary low-cost option may fit. For an exact request such as "fresh red bell pepper" or "dried basil", preserve the requested form. Do not substitute a single product with a mix, ready meal, or drink because of a search-term match.

If no clearly suitable option is found, skip the item. Record the requested product and a concrete reason: no search result, unclear product identity, unavailable at the confirmed store, requirement not met, or unclear price/size comparison. Do not broaden search terms if doing so lowers result quality.
